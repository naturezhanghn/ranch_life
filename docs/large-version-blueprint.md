# 《牧场生活：共同地》大版本蓝图

## 文档目的

这份蓝图把“大版本”拆成可交付的剧情、系统、资产与验收单元。它用于指导主 Agent 调度多个专职 Agent，保证 10 万字剧本能够分批落地到网页版牧场物语，而不是一次性生成无法接入的长文本。

当前版本以 `js/data.js`、`js/state.js`、`js/game.js`、`js/renderer.js` 和 `tests/` 为运行边界。新内容必须沿用现有存档、日结、场景、NPC、员工与 Canvas 渲染入口。

## 大版本目标

玩家在 120 个游戏日内完成“回到牧场—认识彤彤—重建水渠—组建员工队伍—处理旱灾—决定牧场未来”的完整故事。主线有三次不可逆选择，支线由每张地图的人物推动。员工会走动、换岗、劳动、休息，劳动结果可被玩家观察并在日结中核对。

首个线上大版本至少交付以下内容。

- 10 张可到达的地图，包含牧场、牛羊区、鱼塘、村集、港口、工坊、档案室、议事厅、山路和海岛
- 18 名可互动角色，至少 12 名拥有独立个人线
- 7 名可雇佣员工，每名员工有招募、培训、换岗、工资、疲劳、关系和个人剧情
- 种植、浇水、收获、喂养、产奶、剪羊毛、钓鱼、养鱼和贸易形成日循环
- 5 个主结局和 12 个人物结局，结局由玩家的劳动、关系、经营和治理选择共同决定
- 120 个游戏日的日程与事件，每日可观察的 NPC、员工和动物变化
- 100,000 字中文剧情资产，均带唯一 ID、触发条件、角色、地点、状态读写和回退文本

### 每章内部配额

每章按照以下比例拆分，便于不同 Agent 并行生产。

- 主线对白与叙事 4,000 至 6,000 字
- 2 至 4 名人物个人线 2,000 至 3,000 字
- 地图事件与可重复日常对白 1,000 至 2,000 字
- 失败、回退、错过时段和重玩文本 800 至 1,200 字
- 日结、员工报告、牧心记忆摘要 500 至 800 字

## 剧情数据契约

每个剧情节点写成可被程序消费的 JSON 或 ES module 对象。正文文件可分章节保存，运行时由 `js/data.js` 汇总。

```js
{
  id: "ch05_worker_zhouhe_014",
  chapter: 5,
  scene: "farm",
  actor: "zhouhe",
  title: "雨前的秧苗",
  trigger: {
    dayRange: [43, 56],
    requiredFlags: ["worker.farmer.hired"],
    requiredStats: { trust: 18 }
  },
  lines: [
    { speaker: "周禾", text: "今天先看土，不要看表。" },
    { speaker: "主角", text: "你想让我学会什么？" }
  ],
  choices: [
    {
      id: "learn_soil",
      text: "跟着你看土",
      effects: { relation: { zhouhe: 3 }, skill: { farming: 1 } },
      next: "ch05_worker_zhouhe_015"
    }
  ],
  fallback: {
    missed: "雨已经落下来了。周禾把工具收好，约你明早再看。",
    replay: "你们又谈起那块地，周禾记得你上次的选择。"
  },
  recap: "周禾教你先观察土壤，再决定是否浇水。"
}
```

强制字段为 `id`、`scene`、`actor`、`trigger`、`lines`、`effects` 或 `next`。所有效果必须能映射到现有 `state.js`，新增状态要先登记在状态迁移表。每个节点至少有错过文本和重玩文本，避免玩家因错过时间而卡死。

## 角色与地图矩阵

### 主要角色

- 主角：返乡经营者，负责劳动、选择和最终治理签字
- 彤彤：主角妹妹，负责地方关系、家族记忆和失踪线索
- 牧心：牧场 AI，负责观察、记忆、预测和权限请求
- 周禾：种植员工，专注土壤、播种与农民经验
- 林牧：牛羊员工，专注动物照料和牧场边界
- 江岚：钓鱼员工，专注潮汐、鱼群和港口订单
- 沈露：灌溉员工，专注水渠、雨量和节水设备
- 许波：鱼塘员工，专注鱼苗、养鱼和生态平衡
- 唐枝：贸易员工，专注订单、报价和工资结算
- 叶青：巡护员工，专注山路、采集与生态修复

其他 NPC 负责档案、港口、合作社、企业和议事厅。每个 NPC 至少拥有一个工作场景、一个非工作场景和一个关系转折点。

## 主 Agent 多 Agent 监督方案

主 Agent 是项目经理和集成审查者，不能直接把一份长提示词广播给所有 Agent。它维护任务图、剧情状态契约、代码变更队列和验收报告。每个子 Agent 只拥有一个明确产物与一组允许修改的目录。

### Agent 角色

1. **叙事总监 Agent**
   - 维护人物弧线、章节大纲、语气和主题一致性
   - 产出章节提纲与冲突表
   - 不直接修改运行时代码
2. **剧本写作 Agent**
   - 按节点契约生成对白、分支和回退文本
   - 每次提交 4,000 至 8,000 字
   - 只修改 `story/chapters/`
3. **系统接入 Agent**
   - 将已审核剧情映射到 `js/data.js`、`js/state.js` 和 `js/game.js`
   - 必须提供迁移函数、幂等效果和测试
4. **员工与动画 Agent**
   - 实现员工路径、工作动作、工具、疲劳和换岗反馈
   - 只修改 `js/renderer.js`、相关 CSS 和动画测试
5. **美术与声音 Agent**
   - 生成或登记图片、图标、音效和主题音乐
   - 更新 `assets/manifest.json`，不能覆盖既有素材
6. **测试与平衡 Agent**
   - 运行剧情路径、存档迁移、经济模拟和移动端检查
   - 输出 `reports/` 下的验收报告
7. **发布 Agent**
   - 在所有门禁通过后构建、提交、推送和检查 GitHub Pages
   - 不负责修改功能代码

### 主 Agent 的循环

```text
读取 backlog.yaml
  -> 选择当前里程碑和可并行任务
  -> 为每个 Agent 生成带输入、输出、禁止范围的任务卡
  -> 等待提交并读取 changed-files.json
  -> 运行语法、剧情路径、状态、资产和视觉门禁
  -> 失败时只把失败日志和最小修复任务发回原 Agent
  -> 通过后合并剧情索引和代码
  -> 更新 CHANGELOG、存档版本和里程碑状态
  -> 生成下一轮任务卡
```

主 Agent 每轮只允许一个集成提交。它要保存以下文件。

- `orchestrator/backlog.yaml`，任务、依赖、负责人和状态
- `orchestrator/contracts/`，剧情、状态、资产和测试契约
- `orchestrator/reports/iteration-XX.md`，门禁结果和风险
- `orchestrator/decisions.md`，不可逆的设计决定
- `orchestrator/manifest.json`，当前章节、字数和已接入节点

### 任务卡格式

```yaml
id: story-ch05-zhouhe
agent: script-writer
input:
  outline: story/outlines/ch05.md
  contract: orchestrator/contracts/dialogue.schema.json
  existing_ids: orchestrator/manifest.json
output:
  - story/chapters/ch05_zhouhe.json
  - story/reports/ch05_zhouhe.md
allowed_paths:
  - story/chapters/
  - story/reports/
checks:
  - unique_story_ids
  - line_count_and_word_count
  - every_branch_has_fallback
  - every_effect_is_registered
blocked_by:
  - narrative-director-ch05
```

## 剧情与代码验收门禁

### 内容门禁

- 章节累计正文达到配额，重复段落低于 2%
- 每个角色有欲望、阻力、转折和结算
- 每个地图至少有一个主线事件、一个人物事件和一个可重复日常
- 每个选择至少产生一个可观察结果
- 所有错过时段均有回退路径，不锁死主线

### 运行门禁

- `npm run build` 通过
- `node tools/story_paths.js` 能走通五个主结局
- 旧存档能迁移到新状态版本
- 员工工资、体力、产出和剧情效果日结幂等
- 390×844 视口下对话、员工面板和地图交互可操作
- `git diff --check` 通过，资产清单完整

### 视觉门禁

- 员工在岗位路径上移动，停顿时显示工具动作
- 田地、牛羊区、鱼塘和港口至少各有一组劳动反馈粒子
- 减少动态设置能关闭高频粒子而保留关键状态
- 帧率异常时优先降低装饰动画，不删除交互反馈

## 第一轮可直接执行任务

1. 叙事总监整理序章至第二章提纲和 10 名角色关系图
2. 剧本写作 Agent 产出序章 6,000 字并生成节点 JSON
3. 员工与动画 Agent 完成岗位路径和劳动动作
4. 系统接入 Agent 接入序章触发器、状态迁移和日结摘要
5. 测试 Agent 增加 5 条主线、员工工资和旧存档测试
6. 主 Agent 运行全部门禁，生成第一轮报告并合并一个提交

这轮完成后再扩写下一章。这样可以在大版本开发过程中持续得到可玩的网页版本，也能把 10 万字内容分解成可审查、可回滚和可复用的交付物。
